# Phase 2.0 Plan: Zapier Workflow Replacement Expansion

## 1. Cloudflare Worker Updates (`proxy/src/index.ts`)
- **Event Acceptance**:
  - Check the `x-github-event` header. Instead of bailing if it is not `pull_request`, adapt the logic to accept `issues`, `issue_comment`, and (optionally) `push` if desired.
- **Payload Deconstruction**:
  - Branch parsing logic depending on the event type (e.g., pulling numbers out of `payload.issue` instead of `payload.pull_request`).
  - Read `jules:*` label restrictions for issues in the same format.
- **Trigger Enhancements**:
  - Determine appropriate prompt logic based on issue/comment labels combined with event content.

## 2. Notification Dispatch Implementation
- Expand the `Env` interface with `DISCORD_WEBHOOK_URL` and `SLACK_WEBHOOK_URL` optional strings.
- Add an async helper function: `async function dispatchNotification(env: Env, payload: string)`
  - Hits the webhook via generic `fetch` POST.
- Attach `ctx.waitUntil(dispatchNotification(...))` right after Jules is triggered, so the user knows via Slack/Discord that an autonomous task was started.

## 3. Configuration & Deployment
- Update `proxy/wrangler.toml` to list the new required webhook secret variables as comments or template fields.
- Guide the execution of `npx wrangler secret put GITHUB_TOKEN`, `npx wrangler secret put JULES_API_KEY`, etc.
- Execute `npx wrangler deploy` to push the Cloudflare worker live on the edge.

## User Action Required
- Provide Slack/Discord Webhook URLs into secrets.
- Review GitHub event list: what exactly do you want Jules to trigger on for an `issue`? (e.g., when an issue is opened? when it is labeled `jules:review`?)
- Ensure the Github Webhook Settings page is updated to transmit the newly requested event types, as they may have been disabled if only `pull_request` was checked.
