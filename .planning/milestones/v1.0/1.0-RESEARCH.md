# Phase 1.0 Research: Jules Automation Integration

## Objective
Wire up the Jules API for autonomous PR processing and configure internal scheduled tasks for recurring sweeps.

## Current State
- The repository has an existing proxy directory (`/proxy`) initialized with Wrangler (`wrangler.toml`, `src/`) targeting Cloudflare Workers.
- The Python backend elements (`dispatcher.py`, `jules_helper.py`, `check_gh_jules.py`) exist and seem to handle API calls to the main Jules intelligence server and check states.
- `AGENTS.md` clearly outlines dual modes: "Scheduled Sweeps" calling `check_gh_jules.py` and "PR Review Mode" mapping labels (`jules:review`, `jules:test`).

## Core Discoveries & Mechanics

### 1. Webhook Automation (Cloudflare Worker)
We need to implement the Cloudflare Worker inside `proxy/src/`.
- **Trigger**: GitHub Webhook payload (`pull_request` event, `opened` or `labeled` actions).
- **Validation**: Must verify the standard GitHub X-Hub-Signature-256 webhook secret using Web Crypto API.
- **Routing Decision**: Only dispatch the payload to the Python REST backend if the PR labels include `jules:review`, `jules:test`, or `jules:doc`.
- **State Logic**: Check if a webhook status or Check Run already exists before re-posting. Cloudflare worker can invoke the GitHub Checks API natively before firing the backend webhook dispatch to ensure idempotency.

### 2. Submitting to Jules Backend
The Cloudflare Worker will formulate a POST request to the `dispatcher.py` (or a server exposing it) passing the repository details and the specific objective derived from the PR's label (e.g. "Run tests", "Audit PR diff").

### 3. Verification & Guardrails
- **Pre-execution hook exclusion**: The webhook logic shouldn't run forever. Cloudflare Workers have a 30s max duration limit. The worker should queue the event asynchronously, or kick off a long-polling external runner on the server.
- **Testing**: Using `wrangler dev` we can simulate webhooks against the local worker.
- **Dependencies**: Use standard `itty-router` or fetch API for the Worker. No heavy Node APIs.

## Validation Architecture
- **Worker unit tests**: `vitest` should verify the routing logic.
- **End to end**: A mock GitHub webhook should correctly trigger a stub backend.

## Recommendations for Planner
- **Plan 1: Webhook Parser & Validator**: Implement the `proxy/src/index.js (or .ts)` to handle signature validation and PR payload destructuring.
- **Plan 2: Status Checking**: Implement idempotency using GitHub check runs.
- **Plan 3: Backend Dispatch**: Setup the worker to emit external API calls to the remote Jules API dispatcher depending on PR labels.
- **Plan 4: Scheduled Sweep Hook**: Update `AGENTS.md` and define the scheduled CRON within GitHub actions (`.github/workflows/jules-sweep.yml`) that delegates to `check_gh_jules.py` since that accomplishes the sweep requirement.
